# Service templates

> New capabilities are built as modules of `core-python` or `core-rust`, not as new services ([ADR-0017](../../architecture/adr/0017-two-backend-services.md)). Use these templates only to split a module out into its own service when it must scale or fail on its own.

```
just new-service python <name>   # at the repo root, e.g. just new-service python meeting-service
just new-service rust <name>     # e.g. just new-service rust audit-service
```

`new_service.py` copies a template into `microservices/<name>/` and renames `service-template` /
`service_template`. It keeps the service's existing spec (`README.md`). Nothing else in the repo changes.

A new service starts on the templates' default port, 7016. Give it its own free port from the
[port map](../../deployments/README.md#port-map-7000-7030) in its settings (`port`) and its Dockerfile's `EXPOSE`.

## Every service is self-contained

A service never points outside its own folder. It carries:

| | Python service | Rust service |
|---|---|---|
| Project file and lockfile | `pyproject.toml`, `uv.lock`, `.python-version` | `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` |
| Platform code (own copy) | `src/wfk_platform/` | `src/platform/` |
| Contracts | `contracts/proto/wfk/common/v1` (copied common types) and `contracts/proto/wfk/<service>/v1` (its own API) | the same |
| Generated contract code | `src/wfk/` (committed, `just gen`) | `src/contracts.rs` (generated by `build.rs`) |
| Migrations | `migrations/`, applied by `wfk-migrate` (`just migrate`) | `migrations/`, built into the binary (`just migrate`, `<binary> migrate`) |
| Commands | `justfile` | `justfile` |
| Image | `Dockerfile` (build context: the service folder), `python:3.13-slim`, non-root | `Dockerfile`, distroless `cc-debian12:nonroot` |
| Licence policy | `tools/check_licenses.py` | `deny.toml` (cargo-deny) |

The platform code is copied, not shared, so services stay independent. A fix to the platform code goes into the
template first, then into each service that needs it.

Both templates are real, buildable projects, and CI builds and tests them on every change, so a broken template
cannot be copied into a new service.

## What each template gives you

| | Python | Rust |
|---|---|---|
| One port | gRPC only (`grpc.aio`); health is the standard gRPC health service: `""` liveness, `"readiness"` runs the Postgres check | axum and tonic on one listener: HTTP `/healthz`, `/readyz` (Postgres check) and gRPC with `tonic-health` |
| Database | Pool opens without waiting: the service starts while Postgres is down, `/readyz` reports it | Lazy pool, same behaviour |
| Shutdown | SIGINT/SIGTERM: health goes NOT_SERVING, the server drains | Ctrl-C/SIGTERM: graceful shutdown |

See [MIGRATIONS.md](MIGRATIONS.md) for the migration rules. Run the generator tests with `uvx pytest tests` from
this folder.
